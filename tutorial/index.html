1. The whole picture in one diagram

A website is a conversation. Someone's browser asks for a page; your server answers. Django is the machinery that decides how to answer. Almost everything in this course is one of the boxes below.

The one idea to keep: the model (what data exists and how it connects) is the foundation. Pages, URLs and styling are built on top of it and are easy to change. The shape of your data is not. That is why we agree on it first: see the data models lesson.

2. Follow one click, step by step

You are signed in to the example Notes app and open /notes/. Here is what happens, with the file that does each job.

#What happensWhere
1The browser sends GET /notes/ to your server.(the internet)
2Django looks through the URL list for a match: notes/ belongs to the notes app, and its "" entry is the page.mysite/urls.py, notes/urls.py
3The matching view runs. It first checks you are signed in (otherwise it redirects to login).notes/views.py (NotesPage)
4The view picks a template and returns it. This page is a shell; it asks the API for the notes.notes/templates/notes/list.html
5Your browser runs a little JavaScript that calls GET /notes/api/notes/.static/notes/notes.js
6That URL reaches the API viewset, which asks the model for only your notes, and the serializer turns rows into JSON.notes/views.py, serializers.py, models.py
7The database returns the rows. The JSON goes back, the script draws the list./var/data/data/db.sqlite3 on Render

Notice the rule we build by: the API is the foundation and the page is just one customer of it. Tomorrow a phone app could be another customer, with no change to the data layer.

3. The vocabulary

These are the words Claude will use. If one is fuzzy, ask: "what is a migration, in plain words?" is always a good question.

WordPlain meaningHere
ProjectThe whole website: settings plus the apps inside it.mysite/
AppOne feature area as a self-contained folder (Notes, Recipes, Bookings...). Like a room in a house.notes/, core/
ModelA description of one kind of thing you store, written as a Python class. It becomes a table.notes/models.py
FieldOne property of a model: a title, a date, a picture. It becomes a column.title = CharField(...)
Row / instanceOne actual thing: this particular note.a record in the table
RelationshipA link between two models: "a note belongs to a person". The key lesson.owner = ForeignKey(User)
MigrationA recorded, replayable instruction that changes the database to match your models. Like a change log for the data's shape.notes/migrations/
ViewThe code that decides what to answer for a given URL.views.py
URL routeThe rule "this address goes to that view".urls.py
TemplateAn HTML page with holes for data: {{ note.title }}.templates/
Static filesFiles that ship with your code: CSS, JavaScript, logo.static/
Media filesFiles your users upload. Stored on the persistent disk.media/
AdminA free back-office for staff to view and edit any model./admin/
API / RESTURLs that speak data (JSON) instead of pages: create, read, update, delete (CRUD)./notes/api/notes/
SerializerTranslates a model row to JSON and back, and validates input.serializers.py
Settings / env varConfiguration. Secrets and anything that differs between your laptop and production are environment variables..env, Render dashboard

4. Why we build in apps

Picture a house. The project is the building (plumbing, electricity, the front door). Each app is a room with its own furniture. Rules for rooms:

  • A room never reaches into another room's cupboards. (An app never touches another app's data.)
  • Everyone shares the same front door key: one login for the whole building. That is the only thing shared.
  • Each room has its own blueprint on the wall: its docs/<app>/spec.md and data_model.md.

The payoff: you can change, test, or even delete one feature without breaking the others. The long version, with the real mistakes behind each rule, is building_an_app.md.

6. Try it yourself (15 minutes)

Run the site locally (python manage.py runserver), then:

  1. Meet the admin. Create a local admin with python manage.py createsuperuser, open /admin/, find Notes. This is the model, as a form.
  2. Add a note two ways. Once in the admin, once at /notes/. Then open /notes/api/notes/ and see the same data as JSON. Same row, three views of it.
  3. Follow the money. Open notes/models.py and find which field makes a note belong to a person. Ask Claude: "what would break if I deleted that line?"
  4. Break a test on purpose. Open notes/views.py, change filter(owner=self.request.user) to all(), run pytest -q. See which tests fail and read what they say. Then undo it. That test is the reason strangers cannot read each other's notes.
  5. Run the checker. python scripts/verify_site.py --url http://127.0.0.1:8000 and read every line.

Data models and relationships

The most important lesson in this repo. Get the shape of your data right and everything else is easy to change. Get it wrong and every screen inherits the mistake.

1. What is a data model?

A data model is the list of kinds of things your site remembers, what you know about each, and how they connect. Nothing more. It is not code and not screens. You can describe it with a pen and paper.

If you have used a spreadsheet, you already know it:

SpreadsheetDjangoExample
A sheet (tab)Model (becomes a database table)Recipe
A column headingFieldtitle, cooking_time
A rowInstance (one record)"Shakshuka", 25 min
A column of IDs that points at another sheetRelationshipthe recipe's author

Here is one model, as the sheet it becomes:

idtitlecooking_timeauthor
1Shakshuka253
2Lentil soup403
3Challah1805

The id is the row's unique number (the primary key); Django adds it for you. The author column holds a number too: the id of a row in the Author sheet. That little number is a relationship, and it is the subject of this lesson.

2. Fields: describing one thing

For each kind of thing, list what you need to know about it. Each fact has a type:

You know...Field typeNotes
a name, a title (short text)CharField(max_length=200)One line
a description, a story (long text)TextFieldMany lines
a whole number: servings, starsIntegerField / PositiveIntegerFieldNever store numbers as text
money, exact decimalsDecimalFieldNot a float: floats round
yes or noBooleanField"is_published"
a date, or a momentDateField / DateTimeFieldauto_now_add stamps creation time
one of a fixed set: draft, publishedCharField(choices=...)Not free text: typos become new "statuses"
a picture or fileImageField / FileFieldThe file goes to media storage; the row remembers where
an email, a web addressEmailField / URLFieldValidated for you

For each field also decide: is it required or optional? Must it be unique (no two users with the same email)? These small decisions prevent bad data forever.

3. Why relationships matter

Imagine a recipe site that stores the author's name as text inside every recipe:

titleauthor_name
ShakshukaDana Levi
Lentil soupdana levi
HummusDana Levy

Look at what is already wrong: three spellings of one person. Now Dana changes her name, or you want "all recipes by Dana", or you want to email Dana, or Dana deletes her account. Every one of those becomes a hunt through every row, and the site will guess wrong.

The fix is a relationship. Make Author its own sheet, once. Each recipe stores only the author's id. Dana's name lives in exactly one place.

That is the whole reason relationships exist. They give you:

  • One source of truth. A fact is stored once, so it can never disagree with itself.
  • Questions become easy. "All recipes by Dana", "the five best-reviewed recipes", "everyone who reviewed anything" are one-line queries.
  • Safe change. Rename a category once; every recipe shows it.
  • Privacy and permissions. "Only the owner can edit" is only possible if the data says who the owner is. A missing owner link is the root of most privacy bugs.
  • The database defends you. It will refuse a recipe that points at an author who doesn't exist.

4. The four relationships

There are only four shapes. Learn to see them and you can model almost anything. For any two things A and B, ask two questions:

  1. Can one A have many Bs?
  2. Can one B have many As?

Try the two questions

4a. One-to-many (the one you'll use most)

One author has many recipes; each recipe has one author. The "many" side holds the link: the recipe stores the author's id.

class Recipe(models.Model):
    author = models.ForeignKey(Author, on_delete=models.CASCADE, related_name="recipes")
    title = models.CharField(max_length=200)

recipe.author             # the Author of this recipe
author.recipes.all()      # every recipe by this author

Spot it by the words "belongs to": a note belongs to a person, a review belongs to a recipe, an order line belongs to an order.

4b. Many-to-many

A recipe can have many tags (vegan, quick, holiday) and a tag applies to many recipes. Neither side can hold a single id, so the database keeps a small link table in between. Django builds it for you:

class Recipe(models.Model):
    tags = models.ManyToManyField(Tag, blank=True, related_name="recipes")
The "link carries data" trap. Recipes have ingredients, and each link has facts of its own: 200 g of flour. That quantity doesn't belong to the recipe or to the ingredient; it belongs to the link. When the link has its own facts, make it a real model: A many-to-many becomes two one-to-many relationships joined by a model in the middle. Other examples: Student ↔ Course with a grade, Order ↔ Product with a quantity and price, Person ↔ Group with a role.

4c. One-to-one

Each person has at most one profile; each profile belongs to exactly one person. Use it to extend something you don't own. Our rule: if an app needs to remember something extra about a user (a preference, a role), it creates its own profile model linked one-to-one to the user. It never adds fields to the shared User. That keeps every app removable.

class NotesProfile(models.Model):
    user = models.OneToOneField(settings.AUTH_USER_MODEL, on_delete=models.CASCADE)
    default_view = models.CharField(max_length=20, default="list")

4d. The fourth shape: "many-to-one" is just one-to-many seen from the other side

"Many recipes belong to one author" and "one author has many recipes" are the same relationship. In Django there is only one stored link (the ForeignKey on the many side); the other direction is free (author.recipes).

5. What happens when something is deleted?

Every ForeignKey forces you to answer: if the thing it points at is deleted, what happens to me? That is on_delete:

ChoiceMeaningUse when
CASCADEDelete me too.I only make sense with it: a note when its owner is deleted, a review line when its review is deleted.
PROTECTRefuse to delete it while I exist.I'm valuable history: an invoice that points at a customer.
SET_NULLKeep me, forget the link (field must allow empty).I stand alone: a recipe stays when its category is removed.

Say the sentence out loud for each link: "When a user is deleted, their notes should ______." It is a product decision, and it's yours to make, not Claude's.

6. How to find your models

Describe your site in plain sentences, then read the nouns and verbs:

  1. Nouns are candidate models. "Members post recipes, filed in categories, with photos, and other members leave reviews." → Recipe, Category, Photo, Review, Member.
  2. Test each noun. Is there more than one? Does it have facts of its own? Do I need to refer to it from elsewhere? If yes to these, it's a model. If it's just one fact about something else ("the recipe's title"), it's a field.
  3. Facts are fields. "A recipe has a title, a method, a cooking time."
  4. Verbs between nouns are relationships. "Members write recipes" (one-to-many), "recipes have tags" (many-to-many), "members review recipes" (a Review belongs to both).
  5. Ask "who owns this?" for every model that holds personal content. That is an owner link, and it's what privacy depends on.
  6. Draw boxes and lines on paper. If you can't draw it, you don't understand it yet. That's the point of this step.
  7. Test it with questions your site must answer: "Show all recipes by a member." "Average rating of a recipe." "What did this member review?" If a question is awkward to answer from your drawing, the model needs work.
Questions Claude will ask you in the interview (it helps to have thought about them):
  • What are the main things people will create, see or manage?
  • For each: who creates it, who can see it, who can change it?
  • Can one of these belong to several of those, or just one?
  • What must happen to it when its owner leaves?
  • What will you want to count, search or report on in a year?

7. A full worked example: a recipe-sharing site

"Members share recipes, filed under one category, tagged with several tags, made from ingredients with quantities. Other members review them." Here is the data model that falls out of that sentence:

In plain words, this is what you would approve:

Member    1 --- N  Recipe    a member writes many recipes
Category  1 --- N  Recipe    a recipe sits in one category
Recipe    N --- N  Tag       many tags per recipe, and the reverse
Recipe    1 --- N  RecipeIngredient --- N..1 Ingredient
                             (quantity lives on the link)
Recipe    1 --- N  Review    a review belongs to one recipe...
Member    1 --- N  Review    ...and was written by one member

And the questions it answers with no awkwardness: all recipes by a member, all vegan recipes, every recipe using lentils, the average rating of a recipe, who reviewed what. That is how you know the model is good.

8. Common mistakes

A list in a text field: tags = "pasta, vegan"Can't search reliably, typos multiply, can't rename a tagA Tag model and a many-to-many
Real data in a JSON/text file or JSON blobThe app can't see, edit or query it; seeding on every deploy wipes editsModels. Seed once, check for existing rows
Copying a fact into many rows (author name in each recipe)It drifts out of syncStore it once; link to it
Status as free text ("Done", "done ", "DONE")Three statuses, one meaningchoices=[...]

9. Why we agree on this first (migrations)

When you change a model, Django writes a migration: an instruction like "add a column called due_date". Running it changes the database. While the site is empty that is trivial. But once real people have real data:

  • Adding a field is easy. Renaming or splitting one means moving data carefully.
  • Changing a relationship (say, from one-to-many to many-to-many) means rebuilding the links for every existing row.
  • A migration that goes wrong on production data is the kind of mistake you cannot simply undo with git revert (see the rollback guide).

So the order is: interview → thin spec → data model on paper, approved by you → only then code. An hour spent here saves weeks. And later changes are fine; they're just cheaper when you've thought first.

10. Your turn: the data model document

For each app, Claude writes docs/<app>/data_model.md and waits for your approval. Before you say "approved", run this checklist:

  • Can I name every box in plain words, and say why it exists?
  • Does every line read as a true sentence in both directions ("one X has many Y", "each Y belongs to one X")?
  • Have I decided on_delete for each link, in a sentence?
  • Does every model holding personal content have an owner?
  • Is any fact stored in two places? Is any list hiding in a text field?
  • Can the model answer the five questions I'll care about in a year?
  • Do the fields have the right types (numbers as numbers, choices as choices)?

The release train, illustrated

How one small program becomes the only thing that publishes, when several AI sessions build several apps on one repository at the same time.

You probably don't need this page. It is for one situation: more than one app being built at the same time, by several AI sessions, on one repository, with their pushes getting in each other's way. If you build one app, or work in one session at a time, commit, test and push when you decide, as the rest of this blueprint describes, and skip the rest. The train adds moving parts that depend on one computer staying on, and that is only worth it when the collisions are real.

1. Do you need it?

2. The problem it solves

Several AI sessions working on one repository share one live branch. Any of them can push, and a push publishes everybody's commits, not only the pusher's. On the site this was learned on, five sessions on five apps produced, in ten days:

  • a finished feature published by another session in the middle of its own test run;
  • four apps' failures reaching the live site inside other sessions' pushes, unnoticed;
  • a full test run taking three hours instead of one, because several ran at once and fought over the database and the ports;
  • a new app left unregistered for three days, because nobody's scoped tests covered it.

3. The big picture

One small program is the only thing allowed to publish. Each session asks it, with a command called ship. The train tests what the change touches and publishes, or says exactly whose test failed. The full suite runs once a night, for everyone, instead of once per session.

Three things are worth noticing in the picture:

  • The train works in its own copy of the repository. Never in a session's working folder, never in the bot's. Nothing it does can disturb anyone's half-finished work, and nothing half-finished can disturb it.
  • The mail bot is an ordinary developer. It pushes its work to a side branch (side branches do not deploy) and asks the train like everyone else.
  • The board lives outside the repository. Updating it never creates a commit, and every session reads it before starting: what is waiting, what the last train found, and who is editing which shared file.

4. One train, step by step

5. What a train tests

Not everything, by the owner's decision: with a large site the full suite takes an hour, and running it per change would make every publish an hour long. The train reads the files the candidate changes and picks:

What changedWhat runsWhy
One app's own files (its folder, its templates, its static files)Every test file that names that app, plus the site contractGenerous on purpose: a test too many costs seconds, the one missed test is what the train is for
A test fileItself, plus the site contract
Something every app shares: project settings, the main site's code, the requirements, the deploy config, site-wide templatesThe full suiteFor a shared file, "the requester's tests" are everyone's
Documentation onlyNothing
Anything elseThe site contract

The site contract is a short list, a couple of minutes long, of the tests that catch one app breaking another: every installed app is registered, every page answers, the shared stylesheet defines what the markup uses. It runs on every train whatever changed.

Known failures. A file lists tests that are known to fail, each with its owning app, the date and why. The train judges only new failures against it, so the old ones stop hiding the new ones. A line in that file is a debt with a name on it, not a decision: its owner fixes the test and removes the line, and the nightly run says when one started passing.

6. When something fails

The train pushes nothing. It works out which app each new failure belongs to (the app the test file names most), writes that on the board, and mails the owner one short note. Everyone else waits for the next train, which is ten minutes away.

One refinement matters for a site with a mail bot: if a session's change broke the shared folder, the bot's request, which lives on its own branch and never touched that code, is tried again on its own. A client's request should not wait on somebody else's bug.

6b. The first train

The train runs in a clean copy. The tests were written in the developers' copies, which had grown things nobody wrote down. The first real train on a site three years old failed five tests that were not code:

A newer linter. A fresh install took a version two minors ahead with new rules: 461 findings the developers' linter never shows. Setup now reads the tool versions from the shared copy and installs the same.

No built files. A stylesheet test got 404 in the clone and 200 in the shared folder, which had a built folder from some earlier day. Every ride runs the production build step.

No local settings. The local settings file was left out on purpose: it holds real keys. Three tests needed a plain setting that lived next to them. The clone gets a derived copy with every secret-shaped name, every known secret block and every multi-line value removed; a plain setting reaches the tests, a key never leaves the shared copy.

Everyone's old debt. Five more failures were other sessions' and had been failing on the live branch for days. List the known failures, each with an owner, before the first train, or the first requester is blamed for all of them.

The second train died in two seconds: a file copied into the clone by hand stopped git checkout. The clone owns nothing. It is hard-reset before every checkout, and the published script reaches it through the train like everything else.

7. Staying alive

The train runs on one computer that is meant to stay on. Software on a computer like that stops in boring ways: a restart, a hung test, a task somebody disabled. Each has a watcher, and the two unattended programs watch each other.

What can go wrongWhat catches it
The computer restarts mid-trainThe lock names a process that no longer exists; the next tick breaks it and puts the work back in the queue
A test hangsEvery run has a time limit and is killed past it; a lock past its limit is broken
The number of a dead train's process is reused by something elseThe lock remembers when its process started; a different start is a different process, and it is never killed
A session edits the train script while it runsThe task runs the published copy, taken from the train's own clone before each tick
The mail bot goes quiet, or the train doesEach watches the other's heartbeat and mails the owner once
A scheduled task is removed or disabledEvery tick checks both exist and are enabled
The same alert, every ten minutes, foreverEach alert is sent once, again only after twelve hours if still true, and cleared when it stops

8. The rules for every session

  1. Never push the live branch. A hook refuses it. Side branches are fine; they do not deploy.
  2. A commit means "ready to ship". Any train may carry it, so commit only after your own app's tests pass.
  3. When the owner says publish, ask the train and report what it answers.
  4. Run your app's tests while you work. The full suite runs every night, once, for everyone.
  5. Read the board when you start. A failure it names as your app's is yours to fix.
  6. Claim a shared file before editing it (settings, requirements, deploy config), and release it when you commit. A claim expires by itself.
  7. A test you cannot fix now goes on the known-failures list with your app's name, the date and why. Never silently.

9. What it cannot do

The hook is a guard rail, not a wall. It stops accidents by cooperative sessions, which is the whole problem it was built for. A session that decides to push around it can: that is a rule the sessions follow, not a lock on the repository. The hard version is a protection rule on the repository host that lets only the train's own credential push the live branch; it is worth setting up once the train has run for a while.

It cannot survive the computer being off, or on but signed out, unless the scheduled tasks are set to run whether the user is logged on or not. Only the owner can choose that. While it is down, requests wait on the board; nothing is lost, and the owner's emergency override still works.

Per-change testing is a trade. A change in app A that breaks app B through something they share is caught at night, not on the train. The owner chose that trade for speed; the nightly mail is where it shows up.
